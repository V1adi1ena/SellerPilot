## 新增和变化的关键函数

### AuthForm.handleSubmit

注册和登录共用提交状态、错误与取消控制器。注册成功只切回登录，不自动再次注册，也不把密码存入浏览器。登录成功后将JWT交给App，App保存到sessionStorage并读取账号及店铺。组件卸载时取消等待，迟到响应不会登录到旧界面。

### StoreManager.runStoreAction / handleCreate

runStoreAction统一店铺创建和详情读取的锁、取消与401处理。handleCreate发送名称和平台，成功后把服务端返回的Store交给App追加到列表并选中。ID与owner_id由后端决定。

### ProductManager.runAction / loadProducts

runAction为查询、详情、保存和删除提供一个同步ref锁；busy用于禁用控件。每次请求持有自己的控制器，只有仍持有锁的操作才能清理状态。换店铺卸载组件时取消等待。

loadProducts根据商品列表或低库存模式选择后端接口，保存实际查询条件和商品数组；低库存由服务器筛选，不在已截断的列表上本地过滤。

### handleEdit / setField / emptyEditor

handleEdit通过SKU详情接口读取当前商品后再填编辑表单。SKU和store_id不能在编辑时更换。setField使用函数式更新与对象展开，只替换目标字段；keyof Editor限制字段名。emptyEditor为新建操作提供一份独立空表单对象。

### handleSave / refreshAfterWrite

handleSave检查整数库存与DECIMAL价格字符串，按editingSku是否存在选择POST或PUT。创建时店铺ID来自当前Props，不能在表单任意指定。保存成功立即关闭表单，随后刷新列表。

refreshAfterWrite区分“写入成功、读取失败”和“写入失败”，不会因为刷新失败让用户误认为需要重新创建。网络断开导致写入响应丢失时仍可能不确定，商品创建没有新增请求级幂等保证。

### handleDelete / deleteProduct / request

先点击行内删除，再明确确认才发送DELETE。request对204直接返回undefined，不解析不存在的JSON。有关联订单或标题草稿时，后端捕获IntegrityError并rollback，返回409，前端保留商品并展示原因；不级联删除经营历史。

### StoreOperations.loadOperations

新增商品销量请求，与汇总和订单并发读取，三份结果版本不同则提示重查。订单分页和商品销量分页分别保存offset，一方翻页不重置另一方；新日期或状态查询则重新从第一页开始。状态只筛选订单，销售口径由后端固定。

### 路由与依赖拆分

main.py通过include_router注册七个APIRouter。schemas.py只是原有Pydantic模型的归位。dependencies.get_current_user继续验证JWT并读取用户，owned_products_query继续以owner_id限制商品访问。除删除冲突处理外，不改变业务实现。

## 验证及限制

- 拆分前后OpenAPI对比：全部路径、参数、请求响应模型、声明状态码一致，仅增加Swagger分组标签。
- 9项MySQL测试回归通过，覆盖新增的关联商品删除409、未关联商品204、完整商品更新及销量结果；只操作sellerpilot_test，临时记录清理。
- 8组浏览器模拟流程通过，包含注册/建店、商品CRUD、重复SKU、非法金额、删除取消与204、关联冲突、销量分页、原有模块回归、切店与401。
- 桌面1440px、手机390px截图检查通过；金额与币种分别展示，表格在自身区域滚动。
- 商品与店铺列表仍最多100条；没有伪装为总数或新增假分页。打开过的模块在数据修改后需要主动刷新。
- 模型回复仍需人工核对，未重新评估真实GLM完整语义集。部署和空库生产验收不属于这次前端改造。
